【2026年9月】AIエージェントの作り方を解説｜3つの作り方・5つの型・作る前に決める2つのこと

執筆 岡村 希一（nito代表）

AIエージェントを作る手順そのものは、いまは難しくありません。ノーコードのツールなら画面でノードをつなぐだけで動くものができますし、コードで組む場合も、中身はモデルにツールを渡してループさせるだけです。

つまずくのはその後です。動いたものが毎回同じ結果を返さない、権限を持たせすぎて怖くて任せられない、誰も止め方を決めていない。この記事は作り方を3通りに分けて手順を示しつつ、作る前に決めておくと後が楽になる2つのことから先に書きます。設計パターンの出典は2024年12月に公開されたAnthropicのBuilding effective agentsです。

この記事のポイント
  • エージェントとワークフローは別物。決めた道筋をコードで通すのがワークフロー、進め方をモデル自身が決めるのがエージェント
  • 公式が推すのはいちばん単純な方法から始めること。多くの用途では、検索と例を足した1回のモデル呼び出しで足りる
  • 作り方は3通り。ノーコード／既製のエージェント基盤／コードで組む。選ぶ基準は「どこまで自分で直したいか」
  • コードで組むときの型は5つ（プロンプト連鎖・ルーティング・並列化・オーケストレーター／ワーカー・評価と改善）。いきなり自律型にしない
  • フレームワークは着手を速くする一方、抽象化の層がプロンプトと応答を見えなくして、デバッグを難しくする

作る前に決める2つのこと

そもそもエージェントが要るか

Anthropicの記事は、エージェントを作らないという選択肢を最初に挙げています。いちばん単純な解決策から始め、必要になったときだけ複雑にするのが推奨で、多くの用途では検索と例を添えた1回のモデル呼び出しを磨くだけで足ります。

エージェントにするということは、処理時間とコストを払って柔軟さを買うということです。自律的に動く分だけ費用は増え、途中の誤りが後ろの工程に積み上がります。決まった手順を毎回同じようにこなしてほしい仕事なら、エージェントよりワークフローのほうが結果は安定します。

人の承認をどこに置くか

エージェントは人からの指示か対話で仕事を始め、そこからは自分で計画して動きます。公式が重視しているのは2点です。その途中でチェックポイントや行き詰まりで人の判断を仰ぐ形にしておくことと、繰り返し回数の上限のような停止条件を入れておくことです。

これを後から足すのは大変です。メールの送信、ファイルの削除、外部への書き込みのように取り返しがつかない操作を洗い出し、そこだけ人が押す形にしてから作り始めます。

ワークフローとエージェントの違い

言葉の使われ方が幅広いので、公式の定義に沿って整理します。Anthropicは両方をまとめて「エージェント的なシステム」と呼んだうえで、構造の違いをはっきり分けています。

ワークフロー エージェント
進め方を決めるのは あらかじめ書いたコード モデル自身
向いている仕事 手順がはっきりしている仕事 何手かかるか読めない仕事
強み 予測できる、結果が揃う 柔軟に対応できる
弱み 想定外に弱い コストが増え、誤りが積み上がる

自律的なエージェントが向くのは、必要な手数を予測できず、決まった道筋を書けない仕事です。そのかわりモデルの判断をある程度信用する前提になるため、公式はサンドボックスでの十分なテストとガードレールを勧めています。

作り方は3通り

手を動かす方法は大きく3つに分かれます。

作り方 何を使うか 向いている人 引き換えに失うもの
ノーコード Dify、n8n など画面でノードをつなぐツール まず動かして試したい 細かい制御、移植しやすさ
既製のエージェント基盤 Copilot Studio など、業務アプリと一体のもの 既にその業務基盤を使っている その基盤の外に出づらい
コードで組む モデルのAPIを直接、必要ならフレームワーク 自分で直し続けたい 立ち上がりの速さ

選ぶ基準は機能の多さではなく、動かなかったときに自分で直したいかどうかです。直したいならコード、中身に踏み込まないと決めているならノーコードや既製の基盤が向きます。

既製の基盤でCopilot Studioを選ぶ場合の料金と作れる人の決め方は、Copilot Studioの料金で扱っています。

ノーコードで作る場合

Difyを例にすると、流れはアカウント作成、モデルの設定、ワークフローの作成の3つです。クラウド版のSandboxプランには最初に200のAIクレジットが付いており、OpenAIやAnthropic、Geminiのモデルを呼べます。このクレジットは一度きりの付与で、毎月は更新されません。

入力を受け取るノード、自由入力から必要な値を取り出すノード、モデルを呼ぶノードといった部品を、画面上で並べてつなぎます。自然文で書かれた入力を決まった形に直す処理をモデルに任せられるため、後ろのノードが扱いやすくなります。

ここで作れるものの多くは定義上のエージェントではなく、ワークフローに当たります。それで用が足りるなら、無理に自律型にする必要はありません。

Difyのプランごとの料金とモデルのAPI代の見積もり方は、Difyの料金で扱っています。

コードで組む場合の5つの型

コードで組むなら、いきなり自律型を目指さず、公式が挙げる型を順に当てはめます。どれも部品はひとつで、検索・ツール・記憶を足したモデル呼び出しです。

プロンプト連鎖では仕事をいくつかの段に分けて、前の出力を次の入力にします。段と段のあいだにプログラムによる確認を挟めるので、途中でずれたまま進むのを止められます。下書きの骨子を作り、条件を満たしているか確認してから本文を書かせる、といった流れが当てはまります。

ルーティングでは入力を分類して専用の処理に振り分けます。問い合わせの種類ごとに別のプロンプトとツールを使う、簡単な質問は小さいモデルに、難しい質問は能力の高いモデルに回す、といった使い方です。1種類の入力に合わせて調整すると他の入力で精度が落ちる、という問題を避けられます。

並列化には分担と多数決の2つの形があります。分担は独立した小さな仕事を同時に走らせる形、多数決は同じ仕事を何度か走らせて結果を突き合わせる形です。公式はガードレールを別のモデル呼び出しに分ける例を挙げており、本来の回答と内容の審査を同じ呼び出しでやらせるより精度が上がります。

オーケストレーターとワーカーでは、中心のモデルが仕事を分解してワーカーに任せ、結果をまとめます。並列化と形は似ていても、小さな仕事を事前に決めておかない点が違います。修正するファイル数が入力次第で変わるコーディングが、その典型です。

評価と改善は片方が作り、もう片方が評価して戻す往復の形です。評価の基準がはっきりしていて、繰り返すほど良くなる仕事に効きます。人が言葉で指摘すれば明らかに良くなる、そしてその指摘をモデルにも書ける。この2つが揃えば当てはまる型です。

フレームワークをいつ使うか

Claude Agent SDKやAWSのStrands Agents SDKのようなフレームワークは、モデルの呼び出しやツールの定義といった定型の処理を肩代わりしてくれます。着手は確実に速くなります。

一方で公式は、まずAPIを直接使うことを勧めています。多くの型は数行のコードで書けるためです。フレームワークが増やす抽象化の層は、実際に投げられたプロンプトと返ってきた応答を見えなくしてしまい、デバッグを難しくします。単純な作りで足りる場面なのに複雑な仕組みを足したくなる、という副作用もあります。

フレームワークを使う場合でも、中で何が起きているかを理解しておくことが条件です。内部の動作についての思い込みが利用者の失敗によくある原因だ、と公式に書かれています。

動かし続けるための3つの原則

公式が挙げる原則は3つです。

  1. 設計を単純に保つ
  2. 計画の段階を明示して、何をしようとしているか見えるようにする
  3. ツールの説明とテストに手をかけて、モデルとツールのあいだの接点を丁寧に作る

3つ目が見落とされがちです。出典の記事が公開されたあとに変わったのもここで、いまはツールの渡し方にMCPという共通規格が使われます。エージェントの中身は環境からの反応を見ながらツールを使うループにすぎません。どのツールが何をするのか、引数に何を入れるのかをモデルが読んで分かる形で書けているかが、そのまま精度に出ます。

実行中はツールの呼び出し結果やコードの実行結果といった事実を各段階で受け取り、進み具合を自分で確かめられる状態にします。うまくいかないときに設計を疑う前に、まずツールの説明を読み直します。

よくある質問

回答の内容は各ツールの公式ドキュメントの記載と、2026年9月21日時点で確認できた提供条件に基づきます。

AIエージェントは無料で作れますか？

試すだけなら作れる形です。Dify Cloudの無料プランには最初に200のAIクレジットが付いており、モデルの呼び出しに使えます。ただし一度きりの付与なので、使い切った後は自分のAPIキーを設定するか、有料プランに移ります。

プログラミングができなくても作れますか？

ノーコードのツールなら画面でノードをつないで作る形です。ただし動かなかったときに中身を直すには、どこで何が起きているかを読む力が要ります。

ChatGPTはAIエージェントですか？

定義によります。Anthropicの分け方では、進め方をモデル自身が決めて動くものがエージェントで、決めた道筋をコードで通すものはワークフローです。チャットの画面で1往復するだけなら、どちらにも当たりません。エージェントとは何かは別の記事にまとめています。

どのフレームワークを使えばいいですか？

公式はまずAPIを直接使うことを勧めています。多くの型は数行で書けるためです。フレームワークを使う場合も、内部で何が起きているかを理解しておくことが条件になります。

作ったエージェントが毎回違う結果を返します。

手順が決まっている仕事なら、エージェントではなくワークフローに寄せると結果が揃います。決めた道筋をコードで通す形にして、モデルに判断させる範囲を狭めるのが基本です。

暴走を防ぐにはどうしますか？

繰り返し回数の上限のような停止条件を入れ、取り返しがつかない操作の手前に人の承認を置きます。公式はサンドボックスでの十分なテストとガードレールも勧めています。

ガードレールはどう作りますか？

公式が挙げているのは本来の回答とは別のモデル呼び出しで内容を審査する形です。同じ呼び出しに両方をやらせるより精度が上がります。

エージェントを作るべきか判断する基準はありますか？

必要な手数を予測できず、決まった道筋を書けない仕事かどうかです。手順が書けるならワークフロー、1往復で済むならモデルを1回呼ぶだけで足ります。
